# 경험 분석·분해 v2 설계 계획

상태: **핵심 구현 및 전환 완료(2026-10-27, 미커밋)**. 기존 데이터와 UI는 `old` 계약으로 유지하며, 신규 통합·최근 대화·직접 입력 분석은 `experience-units-v2`를 생성한다. 아래의 “현재 코드에서 확인한 위험” 표는 구현 전 기준선이며, 하단 구현 결과에서 대응 상태를 확인한다.

## 구현 결과 요약

| 단계 | 구현 결과 | 검증 |
| --- | --- | --- |
| 1. 검증 기준 | CRLF·Unicode 재조합, 동일 공고 문구, 게스트 개인정보 제외, 긴 입력 부분 실패, 중복 주 소속, V2/legacy 승인을 fixture로 고정 | `test_experience_units.py`, `test_experience_units_api.py` |

사용자 편집은 파생 제목·요약·행동·결과 수정과 단위 삭제·개별 승인까지 제공한다. 원문 구간 자체를 임의로 고치거나 여러 단위에 중복 배정하는 요청은 서버 불변식에서 거부한다. 의미가 불확실한 구간은 자동 병합하지 않고 검토 필요 원문으로 노출한다.

## 목표와 보장 범위

- 입력의 **원문 텍스트와 서식**을 그대로 보존한다. 단, 게스트 입력은 기존 개인정보 제외 규칙을 먼저 적용한 **분석 허용 텍스트**를 100% 보존한다. 가린 개인정보를 새 분석 스냅샷에 되살리거나 AI에 전달하지 않는다. 첨부 원본 파일 보관·삭제 정책은 별도로 따른다.
- 원문 텍스트의 모든 구간을 빠짐없이 분할하고 처리 상태를 남긴다. 경험으로 해석되지 않은 내용도 `미분류`, `일반 정보`, `개인정보 제외`, `공고` 등으로 남겨 누락을 숨기지 않는다.
- 경험 한 단위는 **한 문제/목표와 그에 직접 연결된 행동·결과**만 가진다. 같은 프로젝트의 독립적인 RAG 설계, 성능 실험, 배포는 별도 경험 단위로 저장한다. 프로젝트 이름·소속·기간 등 공통 맥락은 상위 프로젝트에 한 번만 둔다.
- 분석 허용 텍스트의 정본은 출처·개인정보 정책·파서 버전별로 한 번만 저장하고, 실행·경험·사실은 구간 ID를 참조한다. 각 구간의 **주 소속은 하나**이며 다른 경험에서의 맥락·근거 참조는 별도 링크로 허용한다. 동일한 사실이 여러 근거에 나타나면 사실 하나에 근거 여러 개를 연결한다.
- LLM이 모든 의미를 100% 정확하게 해석한다고 보장할 수는 없다. 대신 원문 구간의 100% 보존·분류 상태 기록·빈 구간 자동 검출을 기계적으로 보장하고, 해석이 불확실하거나 `일반 정보`로 분류된 경력 문장은 사용자 검토 대상으로 남긴다. **텍스트 처리 완료와 경험 검토 완료는 별개 상태**다.

## old / new 경계

- **old 읽기·수정·승인 호환:** 기존 `experience_proposal` 액션, `payload.experiences[]`, `ExperienceDraft` 출력, `InlineProposalCard`/`ExperienceDraftEditor`와 이전 API 경로는 과거 초안에 그대로 적용한다. 기존 레코드를 새 형식으로 조용히 변환하지 않는다.
- **new 생성:** 새 분석은 `contract_version: "experience-units-v2"`를 가진 별도 액션과 DTO를 생성한다. 새 백엔드 스키마·서비스와 `src/features/chat/experience-units/`의 컴포넌트·어댑터를 사용한다. 화면은 버전으로 old/new를 분기한다.
- **new 승인:** 배열 인덱스 대신 안정적인 `unit_id`와 `proposal_version`으로 하나씩 승인한다. 서버에서 사용자 소유권·원문 구간·근거·버전·중복 승인을 검증한다. old 승인 엔드포인트와 동작은 유지한다.
- **저장 계층:** `경험 분류 → 프로젝트·활동 → 확정 경험`은 유지한다. new의 `unit_id` 하나가 확정 `Experience` 하나가 되며, 공통 프로젝트 정보는 해당 상위 레코드를 재사용한다. 검색 인덱스는 확정 경험별로 만든다.

## new 데이터 계약 초안

```text
AnalysisRunV2 (사용자, 범위, 정책, 모델/프롬프트/파서 버전, 처리/검토 상태)
  ├─ SourceSnapshot[]  (원본 Message/Attachment 참조, 분석 허용 텍스트의 정본 참조·SHA-256)
  │    └─ SourceSpan[] (source_id, UTF-8 byte start/end, text hash, 분류·처리 상태)
  ├─ ExperienceUnitDraft[] (unit_id, domain/project 참조, 초점, 행동·결과·사실)
  │    └─ UnitSpanLink[] (primary / context / evidence + 필드 위치)
  ├─ CanonicalFact[] (확인된 중복에 한해 통합, 실제 원문 인용과 다대다 연결)
  └─ CoverageReport (바이트 무결성 / 구간 처리 / 의미 검토를 별도로 기록)

승인: ExperienceUnitDraft --unit_id로 1회 승인--> Experience
       AnalysisRunV2 --다대다 링크--> Experience[]
```

원문 분할기는 AI보다 먼저 실행한다. Markdown 제목·목록·문단·공백·코드 블록·표를 **정확한 위치 구간**으로 나누며 각 원본의 구간을 이어 붙이면 분석 허용 원문 바이트와 일치해야 한다. 문장 하나가 여러 독립 사실을 담을 때는 하위 구간으로 더 나누되 부모 구간과 자식 구간의 소유권을 중복 계산하지 않는다. 긴 파일도 모든 청크를 대상으로 분석하고, 청크 사이 중첩 영역은 경계 문맥일 뿐 별도 소유 구간으로 계산하지 않는다.

`SourceSnapshot`의 텍스트는 실행이나 경험마다 복사하지 않는다. 동일한 출처·분석 허용 텍스트 해시·개인정보 정책·파서 버전의 정본을 재사용하고, 실행은 그 정본의 ID와 해시를 참조한다. 원본 Message·Attachment 또는 스냅샷이 삭제·변경되면 링크와 검색 인덱스의 무결성 상태를 갱신한다. 실제 테이블 추가 전에는 `EvidenceDocument`의 원문·청크를 재사용할 수 있는지 확인하되, 줄바꿈 정규화본을 정확한 원문 스냅샷으로 간주하지 않는다.

새 원문 정본과 구간 조회는 기존 `user_id` 권한 경계를 적용한다. 사용자 삭제 시 정본·구간·파생 검색 인덱스를 함께 삭제하거나 삭제 이력만 남기는 정책을 명시하고, 원문이나 개인정보를 운영 로그에 기록하지 않는다. 게스트 개인정보 자동 감지는 완벽하지 않으므로 검출 범위의 테스트와 미검출 시 처리 정책을 별도로 정한다.

첨부 파일의 바이너리 원본과 파서가 추출한 텍스트는 별개의 보존 대상이다. 텍스트 재구성 100%는 **추출된 텍스트**에 대한 보장이고, OCR·파서가 읽지 못한 페이지나 영역은 파싱 품질/미처리 상태로 별도 보고한다. 바이너리 파일에서 읽지 못한 문장까지 추출되었다고 주장하지 않는다.

모델은 기존 자유로운 `experience_drafts[]` 대신 **제공된 구간 ID**를 이용해 경험 단위와 구간 배정을 반환한다. 구간의 근거 없는 값·임의 ID·원문에 없는 수치는 거부한다. 모델이 빠뜨린 구간은 자동으로 `미분류`에 남긴다. 파일·긴 입력은 제한된 크기의 배치로 순차 처리하고 각 배치 상태를 저장한다. 모델 호출 실패나 예산 초과로 남은 배치는 `대기/실패`로 표시하며 처리 완료로 표시하지 않는다. 제목·요약은 파생 텍스트이므로 원문 보존의 대상이 아니며, 행동·결과·수치마다 원문 인용 링크를 붙인다.

API는 `contract_version`을 필수 판별자로 사용하고, new 제안에는 최소한 `analysis_run_id`, `source_snapshot_ids`, `units[{unit_id, project_id 또는 project_draft_id, field_span_ids, status}]`, `coverage{integrity_status, processing_status, review_status, unresolved_span_ids, failed_batch_ids}`를 제공한다. 모든 편집·승인은 배열 위치가 아닌 안정 ID와 제안 버전으로 요청한다. 전송 DTO에는 원문 전체를 경험마다 반복하지 않고 화면이 필요한 구간을 별도 조회한다.

서버가 승인 전에 검사할 불변식:

1. `concat(span.text_bytes)`와 분석 허용 원문의 길이·SHA-256이 일치한다. 원본별 구간은 시작이 0, 끝이 원문 길이이고 틈·겹침이 없다.
2. 각 leaf 구간에 처리 상태가 정확히 하나 있다. 경험/공고/공통 맥락/그 외/미분류/개인정보 제외 중 어디에도 속하지 않는 구간은 허용하지 않는다.
3. 경험에 속한 leaf 구간의 `primary unit_id`는 최대 하나다. 공통 프로젝트 맥락과 반복 인용은 참조 링크로만 공유한다.
4. 모든 `unit_id`, 사실 ID, 출처 ID는 해당 실행·사용자 범위 안에서 유일하다. 동일 사실의 원문 반복은 원문 구간 각각을 보존하고 하나의 사실에 여러 근거로 연결한다. **문구가 비슷하다는 이유만으로 자동 병합하지 않는다.** 의미가 비슷하지만 확신할 수 없는 중복은 검토 표시한다.
5. 초안 삭제·이동·병합·분리 시 구간 소속을 원자적으로 갱신하고, 고아 구간은 `미분류`로 되돌린다. 이미 확정된 경험은 재승인으로 중복 생성하지 않는다.
6. `integrity_status`는 바이트 재조합으로, `processing_status`는 모든 배치 처리 여부로 판정한다. 두 상태가 성공해도 `review_status`가 미확인이라면 **"모든 경험을 찾았다"고 표시하지 않는다.** 미분류·실패 구간이 있으면 부분 처리로 저장하고 재분석할 수 있다. `일반 정보`와 `공통 맥락`으로 분류한 경력 문장도 검토 후보로 드러내어 잘못된 자동 분류가 완료 수치에 숨지 않게 한다.

## 화면 설계

- 상단에 **원문 처리 현황**: 경험 단위 수, 공고, 공통 맥락, 미분류/검토 필요 구간 수를 보여준다. 수치가 0이 아닌 미분류 구간은 숨기지 않는다.
- `경험 분류 / 프로젝트`는 탐색용 헤더다. 그 아래에 **하나의 초점만 가진 작은 경험 카드**를 나열한다. 각 카드에서 문제/목표 → 내가 한 일 → 결과, 원문 근거, 누락·불확실성, 개별 저장 상태를 볼 수 있다.
- 사용자가 카드의 구간을 다른 카드로 옮기거나, 새 카드로 나누거나, 관련 카드끼리 합칠 수 있게 한다. 원문은 편집 전후 같은 자리에서 볼 수 있고, AI 요약 편집은 원문을 바꾸지 않는다.
- 이미지의 Career Memory 사례라면 `원문·Evidence/승인 분리 설계`, `목적별 RAG·LangGraph 흐름`, `v1→v3 성능 실험`, `검증·AWS 배포`를 별도 후보로 검토한다. 정확한 분해는 각 내용의 원문 구간과 근거에 따라 결정하며, 동일 수치·사실을 여러 카드에 복제하지 않는다.

## 구현 순서와 완료 기준

1. **검증 기준 고정:** 개인정보를 제거한 긴 Markdown 입력, 중복 문장, 혼합 공고, 파일, 짧은 대화 답변을 fixture로 만들고 기존 결과·실패를 기록한다. 실제 개인정보와 API 키는 fixture에 넣지 않는다.
2. **원문·구간 기반 마련:** 분석 허용 원문 스냅샷, 결정적 분할, SHA-256 재조합, 처리 상태와 누락 목록을 구현한다. 현재의 문자열 `replace`를 구간 분류로 교체한다.
3. **새 AI·저장 계약:** 모든 구간을 빠짐없이 배치 처리하고, 단위·사실·근거를 검증한다. 통합/직접/파일 경로가 같은 `AnalysisRunV2`를 쓰고 초안·실패·미분류를 영속화한다. 기존 단일 `target_id` 대신 실행↔확정 경험 다대다 링크를 추가하고, `unclaimed_only` 복구 조회도 단위별 승인 상태로 바꾼다.
4. **새 API·화면과 기존 검색 연결:** new 액션·DTO·안정 ID 승인 API와 전용 카드/커버리지 화면을 연결한다. 기존 `Experience`, Evidence 검색, RAG, 공고 매칭이 새 구간 ID 기반 출처를 읽을 수 있도록 어댑터를 먼저 만든다. 호환성이 검증되기 전에는 기존 검색에 필요한 `source_refs` 투영을 유지하며, 검증 후 중복 원문 사본을 제거한다. old 레코드와 컴포넌트는 버전 분기로 유지한다.
5. **회귀·전환:** 원문 바이트 재조합, 구간 중복/누락, 긴 입력 배치, 부분 실패 복구, 게스트 비식별화, 개별/전체 승인, 새로고침과 경험 관리·검색 반영을 검증한다. 새 계약이 이 기준을 통과한 뒤 신규 분석만 전환한다. old 데이터는 그대로 읽고, 원문이 남아 있을 때만 사용자 요청으로 재분석한다.

성공 기준은 카드 수가 많은지가 아니라 **원문 재구성 100%, 처리 상태 없는 구간 0개, 중복 주 소속 0개, 잘못된 인용 0개, 승인 중복 생성 0개**다. 이 수치는 기술적 완전성 기준이며 모든 경험의 의미 추출 성공률을 뜻하지 않는다. 의미 분류가 어려운 구간은 미분류로 드러내고 사용자의 검토 상태를 별도로 표시한다.
