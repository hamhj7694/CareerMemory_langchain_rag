# Career Memory RAG 포트폴리오 정리

## 1. 프로젝트 한 줄 소개

흩어진 대화·텍스트·파일 속 커리어 경험을 AI가 구조화하고, 원본 근거를 보존한 RAG 검색으로 채용공고의 요구사항과 연결해 주는 개인 커리어 메모리 서비스입니다.

## 2. 이 프로젝트에서 보여줄 수 있는 핵심 역량

### 2.1 문제를 제품 구조로 바꾼 경험

단순히 “AI에게 자기소개서를 써 달라고 요청하는 서비스”를 만들지 않았습니다. 사용자가 자신의 경험을 기억하지 못하거나 흩어진 자료를 정리하지 못한다는 문제를 먼저 정의하고, 다음 흐름으로 제품화했습니다.

```text
흩어진 기억과 자료 입력
        ↓
경험 후보 자동 추출
        ↓
사용자 검토·수정·승인
        ↓
확정 경험과 원본 근거 저장
        ↓
채용공고 요구사항별 경험 검색·매칭
```

이 흐름은 생성형 AI의 결과를 바로 확정하지 않고, 사용자의 검토를 거쳐 커리어 자산으로 저장한다는 제품 판단을 보여줍니다.

### 2.2 근거 기반 생성형 AI와 RAG 설계

답변을 그럴듯하게 만드는 것보다 “어떤 경험과 원본 자료를 근거로 답했는가”를 추적할 수 있게 설계했습니다.

- 확정된 경험과 원본 근거를 별도의 RAG 대상으로 관리
- 경험 벡터 저장소와 근거 벡터 저장소 분리
- 대화·파일 원문을 청크로 나누고 원본 위치, 파일 ID, 메시지 ID 보존
- 사용자 ID를 기반으로 Chroma 컬렉션 분리
- 벡터 검색 결과에 원본 근거 ID 연결
- 벡터 검색이 실패할 때 키워드 기반 검색으로 대체
- 콘텐츠 해시를 사용해 변경된 근거만 벡터 저장소에 반영

이 부분은 RAG를 단순한 “문서 검색 후 프롬프트에 넣기”가 아니라, 데이터 출처와 사용자 소유권까지 포함한 검색 시스템으로 구현한 사례입니다.

### 2.3 생성 결과와 확정 데이터의 경계 설계

AI가 추출한 경험은 곧바로 확정하지 않고 초안으로 반환합니다.

- AI가 여러 경험 후보를 추출
- 사용자가 초안을 수정하거나 삭제
- 사용자가 승인한 내용만 확정 경험으로 저장
- 잘못된 초안은 휴지통으로 이동하거나 되돌릴 수 있게 구성
- 확정 경험에 원본 대화·파일 근거 연결

생성형 AI의 환각이나 잘못된 추출 결과가 실제 이력에 바로 들어가지 않도록 사람의 확인 단계를 제품 흐름에 포함한 점을 강조할 수 있습니다.

### 2.4 복수 AI 제공자를 교체 가능한 구조로 추상화

OpenAI에 코드를 고정하지 않고 `AI_PROVIDER` 설정으로 OpenAI와 Gemini를 선택할 수 있게 만들었습니다.

- OpenAI Chat Model과 Embeddings
- Google Gemini Chat Model과 Embeddings
- 공급자별 모델명과 API 키 환경 변수 분리
- 공급자별 임베딩 인덱스 버전 분리
- Gemini 구조화 출력을 기존 OpenAI 형태의 내부 계약으로 변환하는 어댑터 구현

이 설계는 특정 모델에 종속되지 않고 모델 교체, 비용 비교, 장애 대응을 고려한 AI 연동 구조를 보여줍니다.

### 2.5 자연어 대화와 명시적 AI 작업을 하나의 흐름으로 연결

사용자의 입력 의도를 자동 분류해 일반 대화, 경험 정리, 채용공고 분석으로 라우팅합니다.

- `AutoIntentClassifier`로 요청 의도 분류
- 커리어 챗, 경험 구조화, 채용공고 분석을 별도 AI 모듈로 분리
- 대화의 최근 원문, 요약 메모리, 검색된 경험, 첨부 파일 문맥 조립
- 긴 대화는 요약하고 최근 메시지는 별도로 유지
- 채팅 응답은 SSE 스트리밍으로 프런트엔드에 전달

이 부분은 LLM 호출 하나를 붙인 수준이 아니라, 여러 AI 기능을 하나의 사용자 경험으로 통합한 사례입니다.

### 2.6 채용공고 분석을 요구사항 단위로 구조화

채용공고 전체를 한 번에 비교하지 않고, 요구사항을 구조화한 뒤 각 항목별로 경험을 검색하고 매칭합니다.

```text
채용공고 원문 입력
        ↓
요구사항 카드 구조화
        ↓
요구사항별 확정 경험 검색
        ↓
추천 경험과 근거 반환
        ↓
사용자 직접 연결과 AI 추천 구분
```

이를 통해 “이 공고에 맞나요?”라는 모호한 질문을 요구사항별 검토 작업으로 바꾸었습니다.

### 2.7 파일 입력까지 포함한 멀티모달 경험 수집

사용자가 글로 직접 입력하지 않아도 PDF, TXT, 이미지 파일에서 경험을 수집할 수 있습니다.

- TXT 본문 추출
- PDF 텍스트 추출
- 이미지 OCR
- 스캔 PDF 페이지 렌더링 후 OCR
- PDF·이미지 처리 실패 및 파일 제한 오류 처리
- 추출된 텍스트를 경험 분석 AI와 근거 RAG에 연결

`PyMuPDF`, `Pillow`, `pytesseract`, Tesseract OCR을 조합해 실제 자료 입력 흐름을 구현했습니다.

### 2.8 데이터 모델과 API 계약을 함께 설계

프런트엔드와 백엔드가 임의의 JSON을 주고받지 않도록 Pydantic 스키마와 API 계약을 분리했습니다.

- 요청·응답 Pydantic 모델 정의
- 경험, 근거, 초안, 채용공고, 매칭 결과의 데이터 계약 정의
- AI 구조화 출력 검증
- 공개 API 오류 형식 통일
- 프런트엔드 표시 모델과 백엔드 응답 변환 계층 구성
- SSE 이벤트 형식과 채팅 스트림 계약 정의

AI 결과를 화면에 표시하는 것에서 끝나지 않고, 변경 가능한 데이터 계약으로 관리한 점을 어필할 수 있습니다.

### 2.9 사용자 데이터 소유권과 인증을 고려한 설계

커리어 데이터는 민감할 수 있으므로 사용자별 데이터 경계를 코드에 반영했습니다.

- 사용자별 대화·경험·첨부 파일 조회 제한
- 사용자별 Chroma 컬렉션 분리
- Argon2 비밀번호 해싱
- HttpOnly 세션 쿠키
- CSRF 토큰
- 세션 만료 시간
- 다른 사용자의 경험 ID를 직접 알아도 접근하지 못하도록 소유권 검증

생성형 AI 프로젝트에서도 데이터 보안과 소유권을 기능 요구사항으로 다뤘다는 점이 중요합니다.

### 2.10 로컬 실행부터 Windows 배포까지 연결

개발 서버만 만든 것이 아니라, 실제 사용자가 실행할 수 있는 Windows 실행 파일까지 구성했습니다.

- Vite 프런트엔드 Production Build
- FastAPI와 React 정적 파일을 하나의 실행 구조로 통합
- PyInstaller 기반 `CareerMemory.exe` 생성
- 실행 시 로컬 서버 시작 및 브라우저 자동 실행
- 기본 포트가 사용 중이면 다른 로컬 포트 선택
- 사용자 데이터는 `%LOCALAPPDATA%\CareerMemory\data`에 저장
- API 키가 포함된 실제 `.env`는 배포물에서 제외

결과물 실행 검증에서 `/health`, 메인 화면, 채팅 화면, 정적 JavaScript 자산이 정상 응답하고 SQLite DB가 자동 생성되는 것을 확인했습니다.

```text

LangChain Agent와 LangGraph 메모리를 활용한 커리어 대화 파이프라인 구축
ChromaDB 기반 사용자별 경험·근거 RAG 검색 시스템 구현
OpenAI/Gemini 멀티 제공자와 임베딩 모델 교체 구조 설계
Pydantic 기반 AI 구조화 출력 및 프런트엔드·백엔드 데이터 계약 검증

```

## 4. 이력서 bullet 예시

### 짧은 버전

- LangChain·ChromaDB 기반 RAG로 사용자의 커리어 경험과 원본 근거를 검색하고 채용공고 요구사항별로 매칭하는 서비스를 구현
- OpenAI와 Gemini를 선택적으로 사용할 수 있도록 LLM·임베딩 Provider 추상화 및 구조화 출력 어댑터 구현
- Pydantic·SQLAlchemy·FastAPI를 활용해 경험 초안, 사용자 승인, 근거 연결, 인증 API를 설계
- PyMuPDF·Pillow·Tesseract OCR을 이용해 PDF·TXT·이미지에서 커리어 경험을 추출하는 입력 파이프라인 구현
- React·Vite 프런트엔드와 FastAPI 백엔드를 PyInstaller Windows 실행 파일로 패키징하고 로컬 실행 검증

### 설명형 버전

> 흩어진 커리어 자료를 구조화하고 채용공고와 연결하는 Career Memory RAG 서비스를 개발했다. 대화·파일 원문을 경험과 근거로 분리 저장하고, ChromaDB 기반 사용자별 벡터 검색과 키워드 fallback을 구현했다. AI 추출 결과를 바로 확정하지 않고 Pydantic 검증과 사용자 승인 단계를 거치도록 설계했으며, OpenAI/Gemini 교체 구조, FastAPI 인증 API, React 화면, Windows 실행 파일까지 연결했다.

## 5. 면접에서 강조할 설계 판단

### “왜 일반 챗봇이 아니라 커리어 메모리인가?”

일반 챗봇의 답변은 대화가 끝나면 사라지기 쉽습니다. 이 서비스는 대화와 파일에서 경험을 추출하고, 사용자가 승인한 내용만 확정 데이터로 만들어 이후 채용공고 분석과 다시 사용할 수 있게 했습니다.

### “왜 원본 근거를 따로 관리했는가?”

커리어 경험은 사실성이 중요합니다. 경험 요약만 저장하면 AI가 어떤 원문을 참고했는지 확인하기 어렵기 때문에 원본 근거, 파일, 메시지, 청크 위치를 연결했습니다.

### “왜 ChromaDB를 선택했는가?”

개인용 로컬 서비스의 초기 버전에서는 별도 벡터 서버 없이 빠르게 구성하고 데이터를 로컬에 보존할 수 있다는 점을 고려했습니다. 사용자별 컬렉션 분리와 영구 저장을 적용했고, 검색 실패를 대비해 lexical fallback도 구현했습니다.

### “왜 AI 결과를 바로 저장하지 않았는가?”

생성형 AI가 추출한 경험에는 잘못된 역할이나 성과가 섞일 수 있습니다. 따라서 AI 결과를 초안으로만 제공하고, 사용자가 확인·수정·승인한 뒤 확정 경험으로 저장하도록 했습니다.

### “모델이 바뀌면 어떻게 하는가?”

LLM과 임베딩 생성을 Provider 계층으로 분리했습니다. OpenAI와 Gemini를 환경 변수로 선택하고, 임베딩 모델이 바뀌면 벡터 인덱스 버전도 분리해 서로 다른 차원의 벡터가 섞이지 않도록 했습니다.

## 6. 프로젝트에서 특히 내세울 포인트

우선순위를 정하면 다음 네 가지를 가장 앞에 두는 것이 좋습니다.

1. **근거를 보존하는 RAG 설계**
   - 경험·원문·파일·청크 위치를 연결하고 사용자별로 격리

2. **AI 결과를 사람이 검토하는 제품 흐름**
   - 초안 → 수정 → 승인 → 확정 경험의 경계 설계

3. **OpenAI/Gemini 교체 가능한 AI 구조**
   - 채팅, 임베딩, 구조화 출력을 Provider 계층으로 분리

4. **실행 가능한 서비스로 마무리한 배포 경험**
   - React + FastAPI + SQLite + ChromaDB를 Windows 실행 파일로 패키징

## 7. 사실에 맞게 표현할 때 주의할 점

- “모델을 직접 학습했다”라고 표현하지 않고, 외부 LLM API와 RAG 파이프라인을 설계·통합했다고 표현합니다.
- “환각을 완전히 제거했다”라고 표현하지 않고, 원본 근거 연결·구조화 출력 검증·사용자 승인 단계로 위험을 줄였다고 표현합니다.
- “대규모 운영 서비스”라고 표현하지 않고, 로컬 실행 가능한 개인 커리어 관리 서비스와 확장 가능한 API 구조라고 표현합니다.
- OCR은 Python 코드만으로 완결되는 것이 아니라 실행 PC의 Tesseract 설치가 필요하다고 설명합니다.
- 배포 시 실제 API 키가 포함된 `.env`는 제외하고, 사용자가 별도로 설정하는 구조라고 설명합니다.
