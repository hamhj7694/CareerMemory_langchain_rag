CareerMemory 온톨로지·데이터 레이크 점진적 구현 계획
작성 목적: 단기 구현 범위를 검토하고 개발 착수 여부를 결정하기 위한 임시 계획서

======================================================================
1. 목표
======================================================================

CareerMemory의 기존 원문 근거 중심 구조를 유지하면서 다음 두 방향을 점진적으로 공식화한다.

1) 경량 도메인 온톨로지
   - 기술, 직무, 경험, 성과, 채용 요구사항을 명시적인 개념과 관계로 관리한다.
   - 원문 표현을 삭제하거나 강제로 표준화하지 않는다.
   - 검증된 경우에만 원문에 canonical concept ID를 부가 정보로 연결한다.

2) 데이터 레이크 방식의 계층형 데이터 구조
   - 원본, 분석·정규화 데이터, 사용자 승인 데이터를 구분한다.
   - 모든 가공 결과를 원본까지 역추적할 수 있게 한다.
   - 벡터 저장소는 원본 저장소가 아니라 재생성 가능한 검색 인덱스로 취급한다.

이번 단기 작업에서는 Neo4j, RDF/OWL, Spark, Kafka, S3 기반 대규모 인프라는 도입하지 않는다.
현재 SQLite, SQLAlchemy, Pydantic, Chroma 구조 안에서 확장 가능한 기반을 만드는 것을 목표로 한다.


======================================================================
2. 핵심 설계 원칙
======================================================================

- 사용자가 입력한 대화, 파일, 채용공고 원문은 항상 보존한다.
- 정규화에 실패한 규격 외 표현도 unresolved 상태로 보존한다.
- AI 출력은 원본 데이터가 아니라 파생 데이터로 취급한다.
- 구조화 데이터에는 source ID, exact quote, 생성 버전을 기록한다.
- 임베딩은 후보 검색에 사용하고 최종 판정은 명시적인 규칙과 근거로 수행한다.
- Chroma 데이터는 DB와 원본 근거에서 언제든 다시 생성할 수 있어야 한다.
- 기존 API와 프론트엔드 계약은 가능한 한 유지한다.
- 스키마 변경과 기존 데이터 이전은 additive migration으로 진행한다.
- 백필은 기본 dry-run으로 제공하고 명시적인 apply 옵션이 있을 때만 저장한다.

3. 데이터 계층 정의
======================================================================

[Bronze: 원본 데이터]
- 사용자 대화 메시지
- 업로드한 원본 파일
- 직접 입력한 경험 텍스트
- 채용공고 원문
- 파일 해시, MIME type, 생성 시각 등 원본 메타데이터

[Silver: 분석·정규화 데이터]
- 파일 추출 텍스트
- EvidenceDocument
- EvidenceChunk
- SkillMention
- QuantifiedMetric
- ontology concept ID
- 별칭 및 개념 관계
- 임베딩 레코드와 분석 버전

[Gold: 사용자 승인 데이터]
- confirmed Experience
- 승인된 경험 사실과 인용
- JobRequirement
- RequirementExperienceLink
- 사용자 직접 연결 관계

데이터 흐름:

Bronze 원본
  -> 파싱 및 청킹
  -> Silver 근거·정규화 데이터
  -> 사용자 검토 및 승인
  -> Gold 커리어 지식
  -> RAG 검색, 공고 매칭, 이력서·포트폴리오 활용

4. 단계별 구현 계획
======================================================================

---------------------------------------------------------------------
1단계. 아키텍처와 데이터 계층 문서화
예상 기간: 0.5~1일
---------------------------------------------------------------------

[작업]
- Bronze/Silver/Gold 계층의 정의와 책임을 문서화한다.
- 원본 데이터와 파생 데이터의 source of truth를 명확히 한다.
- 데이터 생성, 수정, 삭제, 재분석 흐름을 정리한다.
- 온톨로지 relation type과 매칭 정책을 문서화한다.
- 기존 API 계약에서 변경하지 않을 항목을 확정한다.

[완료 기준]
- 각 데이터가 어느 계층에 속하는지 표로 확인할 수 있다.
- 원본에서 Experience와 Job match까지의 lineage를 설명할 수 있다.
- Chroma가 파생 인덱스라는 원칙이 명시돼 있다.


---------------------------------------------------------------------
2단계. 기술 레지스트리를 경량 온톨로지 DB로 승격
예상 기간: 2~3일
---------------------------------------------------------------------

[신규 테이블 후보]

ontology_concepts
- id
- concept_type
- canonical_name
- description
- status
- ontology_version
- created_at
- updated_at

ontology_aliases
- id
- concept_id
- alias
- locale
- normalization_key
- created_at

ontology_relations
- id
- source_concept_id
- relation_type
- target_concept_id
- matching_policy
- provenance
- ontology_version
- created_at

[초기 relation type]
- alias_of: 동일 개념으로 판정
- related_to: 관련은 있지만 동일하지 않음
- broader_than: 더 넓은 상위 개념
- narrower_than: 더 구체적인 하위 개념

[예시]
- 페스트API --alias_of--> FastAPI
- FastAPI --related_to--> REST API
- JavaScript --related_to--> TypeScript
- FastAPI --narrower_than--> Python Web Framework

[구현 방식]
- 기존 SKILL_REGISTRY를 초기 seed 데이터로 이전한다.
- 기존 SkillMention 스키마를 유지한다.
- canonical_skill_id가 ontology_concepts.id를 참조하도록 한다.
- 정규화 서비스는 우선 DB를 조회하고 안전한 캐시를 사용할 수 있게 한다.
- DB 장애 시 원문을 unresolved로 보존하며 임의의 개념으로 추정하지 않는다.
- 기존 하드코딩 레지스트리는 마이그레이션 기간에 fallback으로 유지할 수 있다.

[완료 기준]
- 기존 기술 별칭 테스트가 동일하게 통과한다.
- FastAPI와 REST API가 동일 기술로 판정되지 않는다.
- 미등록 기술이 삭제되지 않고 unresolved로 저장된다.
- 온톨로지 버전을 결과와 함께 기록할 수 있다.


---------------------------------------------------------------------
3단계. Evidence 계층 영속화
예상 기간: 2~3일
---------------------------------------------------------------------

[신규 테이블 후보]

evidence_documents
- id
- user_id
- source_type
- source_record_id
- original_text 또는 storage_key
- content_hash
- parser_version
- parse_status
- created_at
- updated_at

evidence_chunks
- id
- document_id
- chunk_index
- text
- start_offset
- end_offset
- content_hash
- chunker_version
- created_at

embedding_records
- id
- chunk_id 또는 experience_id
- target_type
- provider
- model
- dimensions
- content_hash
- index_version
- indexed_at

[관계]

Experience Fact
  -> EvidenceCitation
  -> EvidenceChunk
  -> EvidenceDocument
  -> Message / Attachment / JobPosting

[구현 방식]
- 현재 source_refs에서 실행 시 생성하는 근거 문서를 DB에 저장한다.
- 기존 source_ref_id와의 호환성을 유지한다.
- exact quote와 start/end offset을 함께 검증한다.
- 동일 content_hash는 중복 문서 또는 중복 청크로 저장하지 않는다.
- 원본 레코드가 변경되면 파생 Evidence를 stale 상태로 표시한다.

[완료 기준]
- Experience fact 하나에서 원본 메시지 또는 파일까지 추적할 수 있다.
- 동일한 원본을 다시 처리해도 중복 청크가 만들어지지 않는다.
- 원본이 바뀌면 관련 Evidence와 임베딩의 갱신 필요 상태를 알 수 있다.


---------------------------------------------------------------------
4단계. 저장 이벤트 기반 증분 인덱싱
예상 기간: 1~2일
---------------------------------------------------------------------

[처리 흐름]

원본 저장 또는 수정
  -> EvidenceDocument 갱신
  -> EvidenceChunk 생성 또는 변경 확인
  -> content_hash 비교
  -> 변경된 대상만 임베딩
  -> Chroma 추가·수정·삭제
  -> EmbeddingRecord 갱신

[정책]
- content_hash가 같으면 재임베딩하지 않는다.
- 삭제된 Evidence의 Chroma 벡터를 제거한다.
- embedding model 또는 chunker version 변경 시 새 index_version을 사용한다.
- 인덱스가 손상되거나 삭제되어도 DB 데이터로 재구축할 수 있어야 한다.
- 초기에는 API 처리 후 동기 함수 또는 단순 백그라운드 작업으로 구현한다.

[완료 기준]
- 동일 입력의 반복 처리에서 임베딩 API를 다시 호출하지 않는다.
- 수정된 청크만 다시 임베딩된다.
- 사용자별 Chroma collection 격리가 유지된다.
- 전체 인덱스 재구축 명령을 제공한다.


---------------------------------------------------------------------
5단계. 온톨로지 기반 매칭 서비스 분리
예상 기간: 1~2일
---------------------------------------------------------------------

[서비스 인터페이스 예시]
- resolve_concept(raw_name)
- get_relationship(source_id, target_id)
- satisfies_requirement(requirement_concept, experience_concept)
- list_aliases(concept_id)
- list_related_concepts(concept_id)

[최종 판정 정책]
- canonical ID 동일: 충족
- alias_of: 충족
- related_to: 검색 후보 확장만 허용, 필수 요건 충족으로 판정하지 않음
- broader_than/narrower_than: 요구사항별 명시 정책이 있을 때만 충족
- unresolved: 자동 충족 금지, 원문만 보존

[완료 기준]
- skill_normalization.py의 DB 접근과 매칭 정책이 분리된다.
- 임베딩 유사도가 높아도 명시적인 필수 기술이 다르면 최종 추천에서 제외된다.
- 추천 결과에 사용된 concept relation을 설명할 수 있다.

8. 주요 위험과 대응
======================================================================

[과도한 추상화]
- 초기에는 Skill 중심으로 시작하고 실제 필요가 확인되면 Role, Organization,
  Industry, Certificate로 확장한다.

[기존 데이터 손실]
- raw 필드는 유지하고 새 concept ID는 선택적 projection으로 추가한다.
- 마이그레이션은 additive 방식과 dry-run을 사용한다.

[그래프 관계의 잘못된 추론]
- related_to를 exact 또는 alias로 취급하지 않는다.
- 자동 추론보다 명시적인 matching_policy를 우선한다.

[인덱스와 원본 불일치]
- content_hash, parser_version, chunker_version, index_version을 비교한다.
- 인덱스 전체 재구축 기능을 제공한다.

[개인 커리어 정보 보호]
- 모든 개념, Evidence, 인덱스 조회에 user_id 격리를 적용한다.
- 계정 삭제 시 원본, 파생 데이터, 벡터를 함께 제거할 수 있게 한다.

10. 포트폴리오 설명 목표
======================================================================

구현 완료 후 다음과 같이 설명할 수 있다.

"대화·첨부 문서·채용공고 원문을 Bronze 데이터로 보존하고, 근거 청크와
정규화 개념을 Silver 계층으로 구성한 뒤, 사용자 승인 경험을 Gold 커리어
지식으로 관리하는 계층형 데이터 구조를 설계했습니다. 기술 별칭·관련 관계·
미해결 표현을 관리하는 경량 도메인 온톨로지를 구축하고, 임베딩은 후보 검색에만
사용하며 canonical concept ID와 원문 근거 검증으로 최종 매칭을 판정했습니다."
